# 외부 리뷰에 대한 검증 보고

리뷰에서 지적된 8개 항목을 **코드에서 직접 확인**하고, 고칠 수 있는 것은 고치고,
고칠 수 없는 것은 그 이유와 영향 크기를 수치로 냈습니다. 결론부터 말하면 **8개 전부 사실**입니다.

## P0-1 재현 경로 불일치 — 확인, 수정 완료

스크립트가 실제로 읽는 "진짜 입력"(어떤 스크립트도 만들지 않는 파일)을 전수 추출한 결과 4개입니다.

```
raw2/dex2.json        op.gg 도감 원본 (기술·특성·아이템 채용률, 종족값)
raw2/teams2.txt       래더 표본 149팀
tier_new.txt          티어 순위
mvraw/usage_raw.json  기술 채용률 원본   ← 이전 패키지에 누락
```

이전 패키지는 이 중 3개를 `raw/`로 **평탄화해서** 넣었고 `mvraw/usage_raw.json`은 아예 빠져 있었습니다.
또 `exp.mjs`가 완성된 HTML에서 `DEC`를 읽는 **순환 의존**이 있었습니다.

조치:
- 입력 4종을 스크립트가 기대하는 경로 그대로(`raw2/`, `mvraw/`, 루트) 넣었습니다.
- `exp.mjs`의 순환 의존을 제거했습니다(`blk_dec.js`에서 읽습니다).
- 튜닝 상수를 **`config.mjs` 한 곳**으로 모으고 7개 생성 스크립트가 전부 이것을 import하도록 바꿨습니다.
  이전에는 스크립트마다 `Object.assign(CAL, {...})`가 흩어져 있어 서로 달라질 수 있었습니다.
- `rebuild.sh` 한 명령으로 전 과정이 돌아가는지 확인했습니다.
- `MANIFEST.sha256`으로 입력·산출물 해시를 고정했습니다.

## P0-1 보충 — 재현 테스트에서 실제 버그를 잡았습니다

"한 명령 재생성"을 말로만 두지 않고 **zip을 빈 디렉터리에 풀어 실제로 돌렸습니다.** 두 번 실패했습니다.

1. `build2.mjs`가 `mv100.json`·`power100.json`·`mega.json`·`megastats.json`을 **읽어서 없는 항목만 채워 다시 쓰는**
   증분 스크립트라, 이 4개는 "입력이자 산출물"입니다. 빈 상태에서는 시작할 수 없어 `input/seed/`로 분리해 넣었습니다.
2. **`usage.mjs`는 이미 `build2.mjs`에 흡수되어 폐기된 스크립트인데 v1 패키지에 그대로 들어 있었습니다.**
   순서대로 실행하면 `build2.mjs`가 만든 올바른 `usage100.json`(변화기 포함 `all` 필드)을
   옛 형식으로 덮어써서 행렬이 **최대 1.042** 어긋났습니다. 제거했습니다.

수정 후 `usage100.json`·`cov100.json`은 바이트 동일, `V100/V100m/V100u`는 **최대 차이 0**으로 재현됩니다.
지적이 없었으면 못 찾았을 버그입니다.

## P0-2 실제 산출물이 기술 채용률을 쓰지 않음 — 확인. 다만 "고치면 나빠진다"는 결과

지적대로 `mkv2.mjs`의 `mix:0`은 `ttkOne`에서 `mp = usage ? m.p : 1`을 타고,
**그 상대에게 가장 센 공격기를 확률 1로 보유**한 것으로 계산합니다. `slots:0`이라 4칸 제약도 없습니다.
`V100u`(채용률 가중)는 비교용 섹션에만 쓰입니다. "기대 TTK"라는 주석은 **틀린 표현**이 맞습니다.

4칸 제약을 실제로 적용해 봤습니다(`slots:4`). 두 가지로 나눠 측정했습니다.

| 기술 선택 규칙 | ρ50 | ρ100 |
|---|---|---|
| 최대 화력기 상시 보유 (현재) | **0.524** | 0.388 |
| 채용률 가중 기대 TTK (`mix:1`) | 0.476 | 0.383 |
| 공격기 중 상위 4칸만 | 0.501 | 0.320 |
| **변화기 포함 상위 4칸만 (물리적으로 정확)** | **0.428** | 0.327 |

물리적으로 정확한 쪽이 **가장 나쁩니다**. 9,900칸 중 9,815칸이 달라지고 2,434칸이 한 턴 이상 뒤집힙니다.

원인을 찾았습니다. 실채용 상위 4칸 중 **공격기 개수 분포**가 이렇습니다.

```
0칸: 1종(메타몽)   1칸: 11종   2칸: 22종   3칸: 38종   4칸: 28종
```

공격기가 1칸 이하인 12종에는 **5위 하마돈, 31위 님피아, 43위 더시마사리** 같은 상위 카드가 들어 있습니다.
4칸 제약을 걸면 이들의 공격력은 정확히 깎이는데, 그 자리를 차지한
도깨비불·맹독·스텔스록·앙코르·대타출동·하품의 값은 모델이 **전혀 못 잽니다**(쌓기만 근사했습니다).
**제약의 비용만 물리고 편익은 안 주는** 비대칭 수정이라 전체가 나빠집니다.

그래서 이번에는 다음과 같이 처리했습니다.

- `slots`를 `config.mjs`의 정식 옵션으로 만들고 위 수치를 문서에 남겼습니다.
- **기본값은 그대로 두되 표현을 바꿉니다.** "기대 TTK" → **"최대 화력 가정 TTK"**,
  "이 카드가 상대를 넘기는 턴" → **"그 상대에게 가장 센 공격기를 들고 있다고 가정했을 때의 턴"**.
- 이것은 지적하신 "최소한 명확히 표기하라"에 해당하는 조치이고,
  근본 해결은 **변화기의 값을 재는 모델**이 생긴 다음에야 가능합니다(아래 로드맵 1·3단계).

## P0-3 실전 불가능한 능력치 가정 — 확인. 데이터가 없어 보류, 영향은 계량

`st(b)=b+52`, `hpOf(b)=b+107`이 6스탯 전부에 동시에 적용됩니다. 508 예산을 3배 이상 위반합니다.

수집한 원본(`raw2/dex2.json`)의 필드는 `rank, slug, ko, types, stat, moves, abil, item` 뿐이고
**성격·노력치는 애초에 수집되어 있지 않습니다.** 다른 가정으로 바꾸는 건 추측을 추측으로 바꾸는 것이라,
대신 **민감도**를 쟀습니다. 508 예산을 지키는 두 가지 배분을 만들어 비교했습니다.

| 노력치 가정 | ρ50 | ρ100 | 현재 대비 순위 이동(평균/최대) |
|---|---|---|---|
| 전 스탯 252 (현재) | 0.524 | 0.388 | — |
| 공격형 508 (주 공격 스탯 + 스피드) | 0.515 | 0.377 | 6.0계단 / 22계단 |
| 내구형 508 (HP + 주 방어 스탯) | 0.536 | 0.411 | 4.6계단 / 16계단 |

**평균 5계단, 최대 22계단**이 움직입니다. 무시할 크기는 아니지만, 적합도 자체는 거의 변하지 않아
**다른 항목(기술 선택·교체 부재)보다는 2차적**입니다. `config.mjs`의 `evMode`로 세 가정을 전환할 수 있게 해 뒀습니다.
근본 해결은 **성격·노력치를 포함한 세트 표본 수집**이며, 지금 데이터로는 불가능합니다.

## P1-1 1:1 모델과 회복·특성 처리의 충돌 — 확인, 수정 완료

지적이 정확합니다. 두 군데를 고쳤습니다.

| 항목 | 이전 | 수정 후 |
|---|---|---|
| 재생력 | "교체만 하면 발동"이라는 주석과 함께 실효 HP에 반영 | **제거.** 교체가 없는 모델에서 교체 회복을 주지 않습니다 |
| 멀티스케일 | 모든 피격에 ×0.88 | **만피 1발만** 절반 → 필요 턴수에 `+0.5 × 채용률` |
| 필터·하드로크·프리즘아머 | 모든 피격에 ×0.9 | **효과가 굉장할 때만** ×0.75 |
| 이상한비늘 | 모든 피격에 ×0.95 | **중립(1.0).** 상태이상을 모델링하지 않으므로 발동 조건이 없습니다 |

적합도 영향은 ρ50 0.532 → 0.524로 미미합니다. 적합도를 위한 수정이 아니라 **정의를 맞춘 수정**입니다.

## P1-2 팀 최적화가 실제 3v3과 다름 — 확인, 표현 수정

`sqv(S,T)`는 3×3 아홉 쌍의 1:1 값을 단순 평균합니다. 리드·교체·희생·메가 타이밍은 전혀 없습니다.
지적하신 대로 **"팀 상성 점수"**로 이름을 낮추고, 페이지와 문서에서
"추천 팀" → **"이 가정 아래의 후보 팀"**, "최적" → **"이 점수 기준 상위"**로 바꿉니다.
실제 3v3 시뮬레이터는 별도 모델로 두는 것이 맞고, 로드맵 3단계에 넣었습니다.

## P1-3 후보 선별 편향 — 확인, 계량, 수정 완료

지적하신 `opt_full.mjs`의 `Math.max(V[i][j], stone[i]?VM[i][j]:-9)`는
**개체마다 독립적으로 메가값을 취합니다.** 6마리가 전부 스톤이면 6마리가 동시에 메가한 셈이 됩니다.
반면 `nash_full.py`는 한 마리만 메가시킵니다. 두 단계의 가정이 달랐습니다.

크기를 쟀습니다(후보 450팀 기준).

```
기존 대리점수 − 메가 1회 제한 대리점수
  스톤 0장 팀 : 평균 0.000
  스톤 1장 팀 : 평균 0.045
  스톤 2장 팀 : 평균 5.656      ← 2장 팀만 크게 부풀려짐
상위 50팀 겹침 : 34/50           ← 후보 집합 자체가 2장 팀 쪽으로 편향
내시값과의 상관 : 기존 r=0.885 → 메가1회 r=0.938
```

조치: 후보 탐색의 `KEEP`을 150 → **600**으로 넓히고,
뽑힌 600개를 **"한 경기 메가 1회"** 규칙으로 다시 매겨 상위 150만 내시 계산에 넘깁니다.
이렇게 하면 생성 단계와 평가 단계의 메가 가정이 일치하고, 절단 폭도 4배로 넓어집니다.

## P1-4 검증 지표 부족 — 확인. 누수는 계량했고 결과는 "거의 없음"

**평가 누수부터 확인했습니다.** `oppw100`은 래더 149팀의 실측 등장 횟수를 쓰되,
한 번도 안 나온 개체만 `w ∝ (rank+5)^a`로 추정합니다.

```
추정으로 채운 개체 : 6 / 100
그 6종이 전체 가중치에서 차지하는 비중 : 2.1%
```

가중치 방식을 바꿔 ρ를 다시 쟀습니다.

| 가중치 | ρ50 | ρ100 |
|---|---|---|
| 현재(실측+추정) | 0.532 | 0.389 |
| 실측 등장 횟수만 | 0.537 | 0.387 |
| 균등 | 0.537 | 0.401 |

**누수는 구조적으로 존재하지만 효과는 사실상 0**입니다(오히려 균등 가중이 약간 높습니다).
지적해 주신 방향은 맞지만 이 항목은 원인이 아니었습니다.

다만 **나머지 지적은 그대로 유효합니다.** 현재 있는 검증은 ρ와 아이템 Top-1 적중률뿐이고,
기간 분리 홀드아웃·베이스라인 대비·부트스트랩 신뢰구간·실전 승률 검증은 **전부 없습니다.**
특히 배틀 로그가 없어 **경기 레벨 검증 자체가 불가능**합니다. 이것이 현재 가장 큰 공백입니다.

## P2 원천 데이터 복원 불확실 — 확인, 복원 근거 공개

세 군데에서 추정이 들어갑니다.

1. **DP 디코딩** — op.gg가 순위 숫자를 값 앞에 붙여 내보내는 형식(예: 1위·59.8% → `159.8%`)을
   접두 제거 선호 + 단조성 역전 벌점 + 4칸 402% 상한으로 복원합니다(`code/dec2.mjs`).
2. **절단 보정** — 상위 10개만 노출되므로 합이 400%에 못 미칩니다. `min(400/합, 1.6)`으로 스케일합니다.
3. **기본값** — 노출 밖 기술에는 `min(최솟값×0.5, 5)%`를 줍니다.

이번 패키지에 `csv/13_decode_audit.csv`를 추가해 **개체별 원본 합계·보정 계수·노출 밖 기술 수·경고 플래그**를
공개합니다. 보정 계수가 상한 1.6에 걸린 개체는 채용률 신뢰도가 낮으므로 별도로 표시했습니다.

## 로드맵 — 제안해 주신 순서에 대한 현실적 평가

제안하신 4단계에 동의합니다. 다만 **1단계부터 데이터가 막힙니다.**

| 단계 | 필요한 것 | 현재 상태 |
|---|---|---|
| 1. 세트 인식 1v1 | 성격·EV·기술4·아이템·특성의 **결합** 표본 | **없음.** op.gg 도감은 항목별 주변 확률만 제공 |
| 2. 선출 게임 | 1단계 결과 + 메가/테라 자원 규칙 | 규칙은 구현 가능, 보수는 1단계 의존 |
| 3. 상태 기반 3v3 | 턴 엔진(우선도·명중·급소·난수·상태·필드·압정) | 구현 가능. 검증은 4단계 의존 |
| 4. 학습 정책·자기대국 | **실제 배틀 로그** | **없음** |

따라서 우선순위를 이렇게 제안합니다.

1. **데이터 확보가 1순위입니다.** 결합 세트 표본과 배틀 로그가 없으면 1·4단계는 시작할 수 없습니다.
   리플레이·로그를 모을 수 있는 경로가 있는지가 이 프로젝트의 정밀도 상한을 결정합니다.
2. 로그를 기다리는 동안 **3단계(턴 엔진)를 먼저** 만드는 것이 낫다고 봅니다.
   교체·상태이상·압정이 들어가면 지금 억지로 실효 HP에 욱여넣은 재생력·멀티스케일·기합의띠가 자연스럽게 풀리고,
   **P0-2의 "4칸 제약을 걸면 나빠지는" 문제도 같이 해소됩니다**(변화기의 값이 비로소 계산되므로).
3. 결합 세트 표본이 부족하면, 주변 확률의 곱 대신 **클러스터 기반 세트 후보**(공격형/내구형/쌓기형 등)를
   만들고 각 클러스터에 표본 비중을 주는 절충이 현실적입니다. 지금처럼 항목별 독립 곱은 존재하지 않는 조합을 만듭니다.
4. 불확실성 표기는 지금도 가능합니다. 점추정 대신 **부트스트랩 구간**을 붙이는 작업을 다음 순번에 두겠습니다.

지적 네 가지를 전부 확인했고, 세 가지를 고쳤습니다. 수정 후 잠만보는 상위 후보에서 빠졌습니다.

"잠만보가 최적"이라는 신호가 아니라는 지적이 정확합니다.

## 고친 것

**① 회복기는 실채용 4칸 안에 들 때만 회복으로 인정합니다.**
잠만보의 잠자기는 채용률 45.7%로 **5번째**입니다(지진 75.1 · 땅가르기 57 · 하품 53.4 · 냉동펀치 52.6 다음).
4칸에 못 들어가는 기술인데도 실효 HP를 약 7% 올려주고 있었습니다. 이제 잠만보의 회복 가중은 **0**입니다.
아머까오의 날개쉬기(99.3%, 4칸 안)는 그대로 1.0으로 남습니다 — **잠만보만 누르는 규칙이 아닙니다.**

**② 잠자기는 상대에게 쌓기 창을 내주는 것으로 계산합니다.**
2턴을 그냥 내주므로, 내 턴수와 무관하게 상대가 랭크업할 수 있는 것으로 봅니다.
100종 중 잠자기를 20% 이상 채용하는 개체는 **잠만보 하나뿐**이라 사실상 잠만보에만 적용되지만,
규칙 자체는 채용률에서 나온 일반 규칙입니다.

**③ 기여도 분석을 넣었습니다(지적하신 항목).**
팀 빌더에 각 카드를 3픽 후보에서 빼고 5마리(C(5,3)=10조합)로 다시 푼 균형값과의 차이를 표시합니다.
기여도 0.005 이하 + 래더 3회 이하면 **외삽 경고**를 띄웁니다.

## 못 고친 것

**후보 탐색의 상위 2마리 집계**(`opt_full.mjs:23`)는 그대로입니다. 6억 조합을 증분 누적으로 훑는 구조라
전체 합·최악값 집계로 바꾸면 탐색 구조를 다시 짜야 합니다. 대신 **기여도 분석**으로
"이 카드가 실제로 값을 만드는가"를 사후에 직접 보여 주는 방식을 택했습니다.

**1:1 평균 보수**(`nash_full.py:20`)도 그대로입니다. 3v3 시뮬레이터가 있어야 바뀝니다(로드맵 3단계).

## 세트 변형 — 회복·잠자기를 같은 정의 위에 올렸습니다

이전에는 두 개의 임의 게이트가 있었습니다.

```
회복기 : 실채용 "상위 4칸" 안에 들 때만 인정   ← 게이트 A
잠자기 : 채용률 20% 이상이면 모든 매치업에 기점 페널티  ← 게이트 B
```

이제 하나의 확률 규칙으로 바꿨습니다.

```
P(그 회복기를 든 세트) = 채용률
  세트 A (확률 p)  : 회복 있음. 그 기술이 잠자기면 기점 허용도 함께.
  세트 B (확률 1-p): 회복 없음. 기점 허용도 없음.
v(i,j) = Σ p_A·p_B · v(세트 조합)
```

잠만보는 **45.7% 확률로만** 잠자기를 들고, **그 세트에서만** 회복(+7% 실효 HP)과 기점 허용이 **동시에** 붙습니다.
아머까오(날개쉬기 99.3%)는 사실상 항상 회복을 갖습니다. 임의 임계값 두 개가 사라졌습니다.

적합도 영향은 ρ50 0.524 → 0.515로 미미합니다. **적합도를 위한 수정이 아니라 정의를 맞춘 수정**입니다.

## 남은 세트 비일관성 — 인정합니다

지적하신 대로 아직 섞여 있습니다.

| 요소 | 현재 정의 |
|---|---|
| 공격기 | **상대별 최강기를 항상 보유**(`mix:0`) — 4칸 제약 없음 |
| 회복기·잠자기 | 세트 변형(확률 p) ← 이번에 통일 |
| 아이템 | 별도 배분(실채용률 하한) |
| 특성 | 채용률 가중 평균 |

공격기만 여전히 다른 정의입니다. 4칸 제약을 걸면 ρ50이 0.52 → 0.43으로 떨어지는데,
원인은 **상위 4칸에 공격기가 1칸 이하인 개체가 12종**(5위 하마돈 포함)인데
그 자리를 차지한 변화기의 값을 모델이 못 재기 때문입니다(P0-2 참고).

따라서 다음 단계는 제안하신 대로 **클러스터**입니다. 공격형 / 내구형 / 잠자기형처럼 세트 유형을 만들고,
**각 클러스터 안에서만** 공격기·회복기·아이템·특성을 함께 정의하면 이 비대칭이 한 번에 사라집니다.
이번 세트 변형은 그 방향의 **최소 단위 구현**(회복기 1개 기준 2-클러스터)이고, 같은 틀을
공격기까지 확장하는 것이 다음 작업입니다.
