## Phase 1. 코드에서 복원한 모델

각 항목은 `주장 → 파일:라인 → 실제 동작(수식) → 일치 여부 → 문제점` 순서입니다.

### 1-1 1:1 보수 V[i][j]

- **주장**: 승리 = +0.5 + 0.5×(내 잔여 HP 비율), 패배 = −(0.5 + 0.5×상대 잔여 HP 비율), 무승부 = 0
- **위치**: `engine.py:1613-1620` (`simulate`)
- **실제 동작**
  - `ra = a.hp/a.maxhp`, `rb = b.hp/b.maxhp`
  - B 기절 → `+0.5+0.5·ra`
  - A 기절 → `−(0.5+0.5·rb)`
  - 동시 기절 → 먼저 쓰러진 쪽이 짐: `±0.5`, 판정 불가면 0 (`:1615`)
  - `MAX_TURNS=60` (`:57`) 안에 끝나지 않으면 0 (`:1620`)
- **HP 비율의 기준**: 이긴 쪽 자신의 **최대 HP 대비** 남은 비율입니다. 교체 등장으로 한 대 맞고 시작했으면 시작 HP 대비가 아니라 최대 HP 대비입니다.
- **일치 여부**: **일치**
- **기절·교체**
  - 1:1 안에는 교체가 없습니다(한쪽이 쓰러질 때까지 싸움).
  - 교체는 `pre_hit`(등장하면서 공짜 한 대를 맞음, `:1522-1527`)으로만 표현됩니다.
  - 총대장·성묘 같은 마무리 포켓몬은 항상 "동료 2마리 쓰러짐"으로 계산합니다(`engine.py:320`, `Side.fainted`).
- **문제점**
  - 효용 척도(승리 기본 0.5에 HP 보너스 0.5)는 근거 없는 선택입니다 → **휴리스틱**
  - 60턴 무승부를 0으로 두면 HP를 앞서고 있어도 0이 됩니다.

### 1-3 교체 혼합

- **위치**: `engine.value:1656-1661`, `value_vs:1691-1704`
- **실제 동작**: `V = 0.6·duel(A,B) + 0.2·duel(A,B,pre_hit) − 0.2·duel(B,A,pre_hit)`
  - 두 번째 항 = 내가 교체로 들어가 한 대 맞음
  - 세 번째 항 = 상대가 교체로 들어와 한 대 맞음
  - 가중치는 상수 `W_NEUTRAL, W_SWITCH = 0.6, 0.2` (`:1650`)
- **일치 여부**: **일치**
- **추가 확인**: `value(A,B)+value(B,A) = 0.6·[duel(A,B)+duel(B,A)]`가 수치로 성립합니다(최대 오차 1.1e-16, `out_phase3.txt`). 교체 항은 반대칭을 깨지 않습니다.

- 첫 동률만 50:50으로 가르고, 그 뒤 동률은 `ties` 카운터로 번갈아 정합니다.
- 이 카운터에 **첫 동률도 포함되어 있어서**, "B 먼저" 갈래에서는 B가 두 턴 연속으로 먼저 움직입니다(A 먼저 갈래는 A, B, A, …; B 먼저 갈래는 B, B, A, …).
- 그 결과 **같은 세트끼리의 거울전 값이 0이 아닙니다**(`test_mirror_value_zero` 실패):

  | 포켓몬 | value(b, b) |
  |---|---|
  | 메가캥카 | +0.37 |
  | 아머까오 | +0.37 |
  | 망나뇽 | −0.33 |
  | 대쓰여너 | −0.30 |
  | 브리두라스 | −0.29 |

- duel 기준으로는 최대 ±0.61입니다. 결정적 모드에서는 모두 0입니다.
- 선출 보드는 동족전을 실제 값으로 쓰므로(`mirror_zero=False`) 이 오차를 그대로 받습니다.
- 내 파티 대 같은 파티의 3:3 게임 값도 0이 아니라 **+0.0105**입니다(`test_symmetric_data_engine_value_zero` 실패).

### 3-5 메가

- **Nature + prior는 가정입니다.** 메가는 상대가 팀을 짤 때 고릅니다. 코드는 이를 "상대는 알고 나는 모르는 유형"으로 두는데(베이지안 구조로는 정확), prior가 맞는지는 별개의 문제입니다.
- **prior의 합**: 1e-4 미만 조합을 버린 뒤 다시 정규화하지 않아 합이 **0.99999**입니다(`test_probability_normalization` 실패).
  - `solve_bayes`는 내부에서 정규화하므로 결과에는 영향이 없습니다.
  - `worst`와 `y`는 1e-5 수준으로 작아집니다(`pick.py:151,160`). 사소합니다.
- **"메가 없음" / "메가 포켓몬이 선출되지 않음" / "둘 다 선출"**: 모두 올바르게 처리합니다(`stone_sets`의 k=0, `scenario_pick_matrices:113-116`).
- **채용률을 상호배타 확률로 쓰는 문제**: 코드는 그렇게 하지 **않습니다**. 대신 조건부 베르누이를 쓰는데, 여기서 다른 문제가 생깁니다.
  - **채용률을 무시하는 경우**: 팀에 메가 가능 종이 1마리뿐이면 K를 잘라 다시 정규화하므로 P(스톤) = 0.157/(0.083+0.157) = **0.655**로 **pm과 무관**합니다(pm=0.05 → 0.655, pm=0.95 → 0.655).
  - **두 마리일 때**: pm=(0.9, 0.1)이면 P(두 번째가 스톤) = **0.76**으로 채용률 10%를 무시합니다.
  - **그래도 데이터와는 맞는 편입니다**: 레플리카 표본 안에서 실제 스톤 조합의 평균 로그우도는 코드 모델 −1.00, 독립 베르누이 기준선 −1.19이고, 최빈 조합 적중 67.7%입니다. 후보 수별 실제 분포도 비슷합니다(후보 1종 팀 20개 중 75%가 스톤 보유, 후보 2종 팀의 76%가 두 마리 모두 보유).
  - 결론: 구조적으로 pm을 무시하는 것은 **의문**이지만 이 표본에서는 해가 크지 않습니다. 개선 방향은 K를 **후보 수에 조건화**하는 것입니다.
- **엣지 결함**: 스톤 채용률 ≥0.98인 종(루카리오·앱솔·입치트 등 6종)은 기본형이 없어서 `Vb[:,j] = Vm[:,j]`가 됩니다(`pick.py:36,54-55`). 다른 스톤 보유자 c가 메가인 시나리오에서도 j 열이 메가로 남아 **한 배틀에 메가 두 마리**가 됩니다 → **틀림(국소적)**

### 4-1 "추천 내기" = 균형 분포 x의 최댓값

### 4-2 "안전한 조합" = argmax_a Σ_t π_t·min_b P_t(a,b)

- 구현은 정확합니다(`pick.py:160`). 상대가 유형을 알고 최적 대응할 때의 순수전략 보장값이고, 착취 가능성 v − L(a)가 가장 작은 순수전략과 같은 개념입니다.
- 추천 ≠ 안전인 팀 7/12, 안전 조합이 균형 지지 밖에 있는 팀 2/12
- 착취 가능성 중앙값: 추천 0.024, 안전 0.019
- **지지 밖이어도 정상입니다.** 균형은 혼합으로 보장값 v를 얻지만, 순수전략 하나로는 v를 보장하지 못하기 때문입니다. 지지 안의 조합도 혼자서는 v보다 낮고, 순수전략의 최대 보장값은 지지 밖 조합이 가질 수 있습니다.

### 4-3 "상대 예상 선출"

### 4-4 선봉 점수

- **수식**: `score(i) = ½·Σ_j V[i,j]·freq_j + ½·min_{freq_j>0.05} V[i,j]`, `freq_j = P(j 선출)/3`
- **조합 확률과 개별 출전 확률의 혼동**: 명시적 혼동은 없습니다. 다만 freq를 "j가 선봉일 확률"처럼 씁니다. 이는 **선출된 3마리가 같은 확률로 선봉이라는 가정**입니다.
- **상대의 최적 대응**: 고려하지 않습니다. 상대가 내 선봉을 예측해 선봉으로 카운터하는 것을 무시하고, 결정적 규칙이라 읽힙니다.
- **첫 대면만 봄**: 맞습니다. V(1:1 끝장)만 보고 그 뒤 전개는 보지 않습니다.
- **1-6과의 충돌**: 선출 LP의 P는 선봉과 무관합니다. 그래서 선출과 선봉을 함께 정하는 60×60 게임이 아니라, 20×20 해 위에 결정적 규칙을 얹은 구조입니다.
- **측정**: "상대가 내 선봉에 최악 대응(첫 대면 기준)" 규칙의 최선 선봉과 코드 선봉이 다른 팀 3/12. 그 기준에서 손실 중앙값 0, 최대 0.18

### 2. 최소 코드 변경으로 정확도를 가장 크게 올릴 3가지 (구현은 다른 세션에서)

**① 선봉을 게임 안으로 넣기** (`pick.py:162-172` + JS `ui_template.html:276-283`)
- 최소안: 추천 조합마다 3×3 선봉 게임(행 = 내 선봉, 열 = 상대 선봉, 칸 = 첫 대면 값 또는 그 뒤 전개)을 **혼합으로** 풀어, 결정적 선봉 대신 선봉 확률을 보여 줍니다.
- 완전안: 60×60.
- 예상 효과: B 기준 후회 0.93 → 약 0.50(−0.43, 상한). 교체가 있는 실제 게임에서는 이보다 작습니다.

**② 엔진의 라벨 의존 제거**
- 수정 대상
  - `engine.py:1540-1550` 동률: 첫 분기 뒤 번갈아 시작점을 분기 결과의 반대로 두거나, 매 동률을 두 순서로 평균
  - `engine.py:1596-1602` 턴 종료: 스피드 순
  - `engine.py:1461` 날씨 동률
  - 덧붙여 `pick.py:88` prior 재정규화, `pick.py:36/54-55` ≥0.98 종의 메가 두 마리 방지
- 예상 효과: 위반 37/5,565쌍(최대 1.26) → 0, 거울전 ±0.37 → 0(선출 보드의 동족전 칸에 직접 반영), 대칭 데이터 v 0.0105 → 0. Phase 6 FAIL 6건이 모두 통과할 것으로 예상됩니다.

**③ 3:3 집계식 교체 또는 보정** (`team.py:21-26`, `pick.py:121-126`, JS `:256-260`)
- 최소안: 가중을 상수 ½·½ 대신 Model B 행렬에 맞춰 적합합니다(예: `w·avg max + (1−w)·avg min + (1−2w)·avg mean` 꼴을 B 칸에 회귀). 또는 단순 평균으로 바꿉니다.
- 예상 효과: 이번 표본에서 단순 평균은 현재 식보다 B 후회가 0.13 [0.02, 0.34] 작았습니다(6/6팀). 다만 **B 기준 증거일 뿐**이므로 더 많은 팀으로 다시 확인해야 합니다.
- 부수 권고(정확도가 아니라 해석 문제): "내보낼 3마리" 표시를 "혼합 비율대로 뽑기 + 조합별 보장값 표"로 바꾸고, 순수 선택이 필요하면 안전 조합을 권합니다.

### 3. 근본적으로 재설계해야 하는 3가지

**① 3:3을 순차 게임으로 평가**
- ½max+½min 대신 HP 이월·기절 교대·선봉을 포함한 순차 평가(Model B 계열)를 P의 칸으로 쓰고, 전략 공간은 60(조합 × 선봉)으로 둡니다.
- 보드에 쓰려면 사전 계산(자주 만나는 상대 팀)이나 가속(엔진 상태 주입 API, 캐시, 컴파일)이 필요합니다.

**② 배틀 안의 결정을 닫힌 루프로**
- 열린 루프 계획 게임과 상수 60/20/20(Nature로 취급한 교체)을 **턴 단위 선택(교체 포함)의 확률적 게임 근사**(Model C: MCTS·CFR·깊이 제한 탐색)로 바꿉니다.
- B에 교체가 없어 선봉이 과장된 것처럼, 교체의 전략적 가치는 지금 어느 층에도 모델링되어 있지 않습니다.

**③ 숨은 정보와 척도를 팀 수준에서 보정**
- 상대 세트 유형과 메가를 칸마다가 아니라 **팀 수준의 일관된 유형**으로 둡니다. 스톤 prior는 후보 수에 조건화합니다.
- 1:1 효용 척도, λ, /15, alt ½ 같은 hyperparameter를 **실전 기록**(보드에서 수백 경기 수집: 상대 6, 선출·선봉, 승패)으로 승률에 맞춰 적합합니다. 지금은 모든 척도가 임의 상수여서 "값"이 승률로 해석되지 않습니다.
